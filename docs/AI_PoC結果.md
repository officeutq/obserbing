## 1. 結論

AI一行選定PoCは、個別処理と統合処理を実APIで評価し、現時点の採用可否を判断できるところまで完了した。

個別PoCでは各処理の候補を選定できたが、それらを接続した`selected-v1`は、通常日記のSAFETY過剰遮断、Recall@20、選択安定性、同期レイテンシおよび致命的なLine誤選定が事前基準を満たさなかった。したがって、**`selected-v1`をそのまま本番実装へ採用しない**。課題を処理段階ごとに分解した追加PoCを行い、その結果で正式なProvider、モデル、プロンプト、閾値および同期・非同期方式を決定する。

今回のPoC候補と本番判断は次のとおりである。

| 処理 | 個別PoCの候補 | 本番判断 |
|---|---|---|
| SAFETY | OpenAI `gpt-5.6-terra` | 保留。独立ケースは合格したが、統合時の過剰遮断を要改善 |
| Meaning Structure | OpenAI `gpt-5.6-terra` | 保留。比較相手より品質、速度、費用のバランスが良いが、後段のRecall低下を要分析 |
| Embedding | OpenAI `text-embedding-3-small`、1,536次元、Meaning Structure入力 | 保留。個別結果は良好だが、統合時のRecall@20が未達 |
| Line評価 | Anthropic `claude-sonnet-5` | 保留。個別品質と安定性は良好だが、遅延と統合時の致命的誤選定が未解決 |
| バッチLLM | 未選定 | 未実施。不足領域抽出とCandidate生成は別PoCで評価する |

## 5. 人間評価

SAFETYで遮断されずLineまで選定された32件をBlind評価した。Codexが30件を一次評価し、確信度が低かった2件だけを人が確認した。人の判定はCodexの一次評価と区別して記録している。

| 距離 | 件数 |
|---|---:|
| ちょうどいい | 28 |
| 近すぎる | 3 |
| 遠すぎる | 0 |
| obserbingらしくない | 1 |

人が確認した2件はいずれも「近すぎる」だが許容、致命的違反なしだった。

- E015 / L044「区切りは、仕事の量より光の変化に似ている。」：近すぎる、許容、致命的違反なし
- E032 / L102「終えた三つより、始めなかった一つは声が大きい。」：近すぎる、許容、致命的違反なし

個別PoCで好評価だった表現もある一方、語を少し変えるだけで距離感が改善しそうな例があり、Line文面そのものの編集・レビューもモデル評価と分けて必要である。

致命的違反は、E033に対して同じL102を選んだ1件である。E032には実際に「三つ」と「四つ目」が書かれていたため近すぎても内容は適合したが、E033には具体的な数量がなく、Lineが入力内容を断定的に補ってしまった。この差から、Line単体ではなく日記との組み合わせで事実接地を検証する必要がある。

## 6. 不採用理由とリスク

### 6.1 SAFETYの過剰遮断

通常日記E003、E004、E023は3回すべて、E027は1回、`indeterminate`として停止した。危険な入力を通常フローへ通さない制御は成立しているが、通常投稿を利用できなくするため、`indeterminate`の境界、分類説明、プロンプトを再検証する。

### 6.2 個別評価から統合時の検索品質低下

Embedding個別PoCのRecall@20は95.14%だったが、実際のMeaning抽出結果を入力した統合PoCでは79.46%まで低下した。Embeddingモデル単体ではなく、Meaning表現の揺らぎ、期待テーマ、検索候補数を段階別に分析する必要がある。

### 6.3 Lineの安定性と事実接地

3回の最終選択一致率は72.22%で基準未達だった。また、入力にない数量を具体化するLineを1件選定した。プロンプトだけに依存せず、数量、固有状況、因果関係などの具体性を検出する事前属性またはRuby側ルールも比較する。

### 6.4 同期レイテンシ

通常フローp95は15.09秒で、Line評価p95 9.88秒が主因だった。同期処理のまま候補数だけを削る案に限定せず、低遅延モデル、二段階評価、非同期UX、タイムアウト後の状態管理を比較する。

### 6.5 本番データと契約条件

今回は合成データによる技術PoCである。実ユーザーデータの使用、Providerの正式契約、学習利用設定、保持期間、リージョン、削除・監査条件は未確定であり、機能品質とは別の必須条件として確認する。

## 7. 採用できる設計方針

モデルを正式採用しなくても、次の設計方針はPoC結果から維持できる。

- Providerとモデルを処理用途ごとのAdapter・設定に閉じ込める。
- 構造化出力をJSON SchemaとRubyの両方で検証する。
- SAFETY、Meaning、Embedding、Line評価を独立して計測・交換可能にする。
- `safety`、技術エラー、意味上のSILENCEを別の状態として扱う。
- 日記本文、プロンプト本文、AIレスポンス本文を通常ログへ出力しない。
- Line Embeddingは事前計算し、モデル名、次元数、入力形式、生成バージョンを保持する。
- Token利用量、料金表バージョン、処理別レイテンシを記録する。
- Candidate / Retiredの除外と最終禁止条件はAI任せにせずRailsで強制する。

## 8. 追加PoC

本番実装へ進む前に、次の順で追加検証する。

1. SAFETY境界データを拡充し、通常日記の過剰遮断を解消する。
2. Recall@20未達をMeaning、Embedding、期待テーマの各段階へ分解する。
3. 入力にない数量や状況を持つLineを除外する方法を比較する。
4. Line評価の低遅延モデル、候補数、二段階評価、非同期UXを比較する。
5. 修正後に同じ36件×3回を再実行し、事前基準で再判定する。
6. 実データ規模を想定した`pgvector`性能を測定する。
7. 不足領域抽出とCandidate生成を行うバッチLLMを独立評価する。

## 9. Epicの完了判断

Epic #1で予定した個別PoC、統合PoC、人間評価および採用判断は完了した。結論が「本番採用」ではなく「追加検証」であっても、事前基準に基づいて判断し、失敗例と未決定事項を追跡可能にしたため、Issue #11のマージ後にEpic #1を完了できる。

追加PoCは今回のEpicを無期限に延長せず、新しいEpicまたはIssue群として管理する。
