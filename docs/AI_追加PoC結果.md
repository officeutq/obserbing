# AI追加PoC結果

**文書ステータス：Epic #27 最終評価・Issue #36ライブ追補完了**

**作成日：2026年8月13日**

**関連Issue：#19〜#27、#36**

## 1. 結論

`selected-v1`と`abstraction-only-v1`は、どちらも現状のまま詳細設計候補にしない。初回方式は比較baselineとして維持し、追加方式は診断用`abstraction-only-v1-diagnostic`として成果物を保持する。本番正式採用方式、Provider、モデル、契約、プロンプトおよび閾値は未決定のままとする。

追加方式はIssue #36のライブ統合で、既存通常日記のSAFETY過剰遮断0件、リアルタイムLine評価LLM 0回、外部API基本3段階、1投稿約0.551円、p95 5.48768秒を実測した。しかし、重要ケース補正後のBlind許容率74.07%、baseline差-22.81ポイント、Top 20候補集合Jaccard平均0.672、致命的事実不整合1件で固定基準を満たさなかった。速度と費用の改善だけでは最終Line品質の低下を受け入れられない。

初回方式はBlind許容率96.88%とRecall@50 95.60%が良好だった一方、通常日記4 / 36件のSAFETY過剰遮断、Recall@20 79.46%、最終選択一致率72.22%、p95 15.09秒、致命的事実不整合1件が残る。こちらも必須条件を満たさない。

したがってIssue #26の選択肢は「どちらも見送る」とする。ただし、追加PoCで基準を満たしたSAFETY `additional-v3`、abstraction `abstraction-only-v2`、事実整合ガード`combined_v1`は、次方式を検討する際の部品候補として維持する。これは本番採用を意味しない。

## 2. 比較条件と証拠

- 共通母集団：既存合成日記36件、Approved Line 96件、各3反復
- baseline：初回PoC `selected-v1`
- 追加方式：不適格要素を含むため正式候補ではなく、`abstraction-only-v1-diagnostic`
- 主基準：Issue #19で結果閲覧前に固定したBlind許容性、非劣性、事実整合、安全性、安定性、性能および費用
- baseline値：[統合PoC比較](統合_PoC比較.md)の公表済み結果
- 追加方式値：[Abstraction Only 統合PoC比較](Abstraction_Only_統合PoC比較.md)、[Abstraction Only ライブ統合追補](Abstraction_Only_ライブ統合追補.md)と版付き集計

Issue #25時点では追加方式の全段階を一から再実行する試行がOpenAIの`credit_balance_exhausted`で停止したため、#20〜#22の保存済み実Provider出力を接続して評価した。その後APIクレジットを追加し、Issue #36で同じ36件×3反復をライブ統合した。以下の追加方式欄はライブ結果を正とし、リプレイとの差と実行経過は[Abstraction Only ライブ統合追補](Abstraction_Only_ライブ統合追補.md)に記録する。

## 4. 距離と失敗例

| 距離 | `selected-v1` | `abstraction-only-v1-diagnostic` |
|---|---:|---:|
| `just_right` | 28 | 66 |
| `too_close` | 3 | 31 |
| `too_far` | 0 | 10 |
| `not_obserbing` | 1 | 1 |

追加方式はLine評価LLMを外したことで、類似度の高い候補を「近すぎる」と判定する機構と、抽象的な接点が弱い候補を「遠すぎる」と判定する機構を失った。重み付き乱択はTop 1固定より分布を改善したが、適切なobserbing distanceを保証できない。

致命的事実不整合は次の通りである。

- baseline E033 / L102：入力に数量がないのに「三つ」「一つ」を具体化した。
- 追加方式 E001 / L083：入力の「二つの案」を「選んだ一人」「選ばなかった誰か」という人物へ具体化した。

`combined_v1`は既知の数量・箱等を除外できたが、「案」を「一人・誰か」へ置き換える人物具体化を検出できなかった。静的語彙ガードは防御層として有用だが、未知の具体的主張を完全には一般化できない。

## 6. 候補集合・選択安定性

| 指標 | `selected-v1` | `abstraction-only-v1-diagnostic` | 固定基準 |

| 3反復の最終Line完全一致 | 72.22% | 2.78% | 診断 |
| 同一候補・同一seedのRuby再現 | Ruby決定的 | 100% | 100% |
| status・再利用・禁止・ガード後違反 | 0 | 0 | 各0 |

両方式の検索診断指標は定義が異なるため、RecallとJaccardを直接大小比較しない。重要なのは、どちらも各方式に事前設定した基準を満たさなかった点である。追加方式ではRuby乱択自体は決定的でも、生成abstractionと候補集合が反復ごとに変わるため、End-to-Endの最終Lineは安定しなかった。

## 8. 採用判断

| 選択肢 | 判断 | 根拠 |
|---|---|---|
| `abstraction-only-v1`を詳細設計候補にする | 不採用 | 品質、非劣性、候補安定性、事実整合が未達 |
| baseline方式を候補として維持する | 比較baselineとしてのみ維持 | 品質は高いがSAFETY、速度、安定性、事実整合が未達 |
| 現方式を組み合わせてそのまま詳細設計へ進む | 不採用 | `additional-v3`とガードだけでは品質・事実整合を閉じない |
| どちらも見送る | **採用** | 必須基準を満たすEnd-to-End方式がない |

本番方式は未決定である。次に検証するなら、追加PoCで有効だったSAFETYと静的ガードを残しつつ、次の2点を独立に解く必要がある。

1. 制御語彙や複数の相補表現により、候補集合の上流安定性を改善する。
2. 低遅延のgroundedness / obserbing distance評価をガード後候補だけへ適用し、未知の具体的主張と距離不適合を検出する。

完全にLLMなしの最終選択へ固執しない。一方、初回と同じ高遅延Line評価をそのまま戻さない。実装候補を作る場合は別Epicで事前基準を固定し、今回確立した単件End-to-End実行とテレメトリ台帳を使って新しい版として評価する。
